# 토큰 절감 실험 작업일지

개인 Agent가 요청 하나에 쓰는 모델 호출과 토큰을 줄이는 과정을 기록한다. 각 항목은 문제, 가설, 바꾼 것, 측정, 결과, 다음 판단 순서로 적는다.

## 2026-11-04 준비

**문제.** 요청 대부분이 모델을 2~4번 부른다. 고정 문형이나 같은 질문에도 매번 모델을 거친다. 줄일 여지가 얼마나 되는지 숫자가 없다.

**가설.** 코드 라우터, 답변 캐시, 도구 목록 줄이기, 계획 1회 후 코드 실행을 적용하면 유형별로 호출이 줄어든다. 성공률이 떨어지는 방법은 채택하지 않는다.

**한 것.**
- Codex 작업과 충돌하지 않도록 별도 worktree `D:\univ\assistant-bench`, 브랜치 `bench/token-experiments`를 만들었다. 기준은 `origin/feat/android-discord`의 `aa4b129`다.
- `bench/requests.jsonl`: 기준 요청 20개를 유형별로 고정했다. 단순 질문 4개(그중 1개는 다른 표현의 중복), 고정 명령 4개, 도구 1개 5개, 여러 단계 4개, 앱 조작 3개다. 면접과 채용 관련 요청은 넣지 않았다.
- `bench/stubs.py`: 실제 운영 도구 24개의 이름과 입력 형식은 그대로 쓰고, 결과만 가짜로 돌려준다. 실험 중 메시지 전송이나 계정 접근이 일어나지 않는다.

**처음 측정한 크기.**
- 모델에 매번 함께 보내는 도구 설명: 24개, 약 7,100자
- 시스템 지시문: 약 1,600자
- 요청 문장 자체는 대부분 30자 안팎이다. 입력 토큰의 대부분이 도구 설명과 지시문이라는 뜻이고, 도구 목록 줄이기가 가장 큰 후보다.

**중단과 방향 전환.** 구독 모델을 실험용으로 수백 번 자동 호출하는 비교 코드를 쓰다 안전 검사에 걸려 멈췄다. 정확한 사유는 나오지 않았다. 의심되는 부분(구독 경로 대량 자동 호출)을 빼고, 모델을 전혀 부르지 않는 오프라인 측정으로 바꿨다.

## 2026-11-04 오프라인 측정 1차

**측정 방법.** `bench/measure.py`가 `o200k_base` 토크나이저로 모델 호출 1회당 입력 토큰을 계산한다. 모델은 부르지 않는다. 결과 전체는 `bench/results.md`에 있다.

**시행착오.** 도구 고르기 첫 버전은 "알려줘"만 있어도 예약 도구를 붙였다. "리스트 뒤집는 방법 알려줘" 같은 단순 질문 2개에 예약 도구가 잘못 붙어 테스트가 실패했다. 예약 판단에 시간 표현이나 알림·예약 단어를 요구하도록 좁혔다.

**결과(요청 20개 합계, 호출 1회당 입력).**

| 방식 | 입력 토큰 | 기준 대비 |
| --- | ---: | ---: |
| A 기준(도구 24개 전부) | 64,474 | - |
| B 필요한 도구 묶음만 | 23,792 | -63.1% |
| C B + 설명 첫 문장만 | 22,522 | -65.1% |
| D C + 코드 라우터 + 답변 캐시 | 12,693 | -80.3% |

- 도구 설명 24개가 2,371토큰으로 지시문 840토큰의 약 3배였다. 요청 문장은 평균 13토큰이다. 입력의 대부분이 매번 같은 도구 설명이었다.
- 코드 라우터가 20개 중 8개를 모델 없이 처리했다(예약, 예약 목록, 기억, 경로 2개, 장소 검색, 앱 열기). 답변 캐시는 다른 표현의 같은 질문 1개를 처리했다.
- 설명을 첫 문장으로 줄이는 효과(B→C)는 2%p로 작았다. 줄인 설명이 모델 판단을 흐릴 위험에 비해 이득이 작아 우선순위를 낮춘다.

**한계.**
- 호출 1회당 입력만 셌다. 실제 요청은 여러 번 호출하고 도구 결과도 입력에 쌓이므로, 실제 절감 비율은 이 표와 다를 수 있다.
- 요청 세트를 직접 만들어서 라우터 적중률(8/20)이 낙관적이다. 실제 대화 기록으로 다시 재야 한다.
- 도구 고르기가 필요한 도구를 빠뜨리면 모델이 일을 못 한다. 빠졌을 때 전체 도구로 한 번 더 시도하는 안전장치가 필요하고, 그 비용도 따로 재야 한다.
- 단순 질문은 도구를 빼면 지시문(840토큰)이 입력의 대부분이 된다. 다음 후보는 지시문 줄이기다.

**다음 판단.**
1. 운영 Agent에 B(도구 묶음 고르기)와 D(라우터, 캐시)를 먼저 적용한다. 효과가 가장 크고 코드만으로 된다.
2. 실제 운영 응답의 토큰 기록을 모아 적용 전후를 비교한다. 실험용 추가 호출은 하지 않는다.
3. 도구 누락 시 전체 도구로 다시 시도하는 비율과 비용을 잰다.
