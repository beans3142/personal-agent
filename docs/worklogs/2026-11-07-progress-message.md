# 요청 진행 상황을 메시지 하나로 보여주고 그 메시지를 답변으로 바꾼다

> 2026-11-07 · 미커밋 · 요청 직후 상태 메시지를 보내고 도구 실행마다 고쳐 쓴다

## 무엇이 문제였나

휴대폰 조작 요청 하나에 182초가 걸렸다. 그동안 채널에는 ⏳ 반응과 입력 중 표시만 있었다. 소유자는 대비스가 무엇을 하는지, 어디서 멈췄는지 알 수 없었다.

## 왜 그런 일이 생겼나

게이트웨이는 Hermes 프로세스가 끝날 때까지 기다렸다가 답을 한 번에 보냈다. 도구 호출은 별도 프로세스인 MCP 서버에서 일어나기 때문에, 게이트웨이에는 중간 상태가 전달되지 않았다.

## 고를 수 있던 방법

| 방법 | 장점 | 버린 이유 또는 고른 이유 |
| --- | --- | --- |
| Hermes 출력을 실시간으로 읽기 | 모델의 생각 단계까지 보인다 | 실행기 출력 형식을 바꿔야 하고, 모델이 쓴 문장이 채널에 그대로 노출될 수 있어서 버림 |
| MCP 서버가 도구를 호출할 때마다 작업 폴더에 한 줄씩 기록 | 모든 도구가 한 곳을 지나간다. 결제 승인 때 쓰는 폴더와 같은 폴더다 | 고름 |
| 단계마다 새 메시지 보내기 | 구현이 단순하다 | 채널이 금방 지저분해져서 버림 |

## 바꾼 것

- `agent/progress.py`를 새로 만들었다.
  - 도구 호출 기록: `<outbox>/progress.jsonl`에 도구 이름만 쓴다. 앱 열기만 앱 이름을 같이 쓴다. 메시지 본문, 받는 사람 같은 인자는 쓰지 않는다.
  - 화면 표시: 도구 이름을 "화면 확인", "글자 입력" 같은 한국어 단계로 바꾼다. 같은 단계가 이어지면 `×N`으로 묶는다. 화면에는 최근 6단계만 보여준다.
  - 상태 메시지(`ProgressMessage`): 요청을 받으면 바로 보내고, 2초마다 확인해서 단계가 바뀌었을 때 고쳐 쓴다. 경과 시간만 바뀐 경우에는 10초마다 고쳐 쓴다. 작업이 끝나면 이 메시지를 답변 첫 부분으로 바꾸고, 2000자를 넘는 나머지는 새 메시지로 보낸다.
- `mcp_server.py`: 도구를 호출할 때마다 진행 기록을 남긴다. 허용된 도구이고 인자 검사를 통과한 호출만 기록한다. 기록에 실패해도 도구는 그대로 실행된다.
- `gateway.py`: 요청이 들어오면 상태 메시지를 시작한다.
  - 대화 주제 선택이 필요할 때와 PC 종료 영수증 메시지가 따로 있을 때는 상태 메시지를 지운다.
  - 상태 메시지를 보낼 권한이 없으면 기존처럼 답변을 새 메시지로 보낸다.

## 확인한 것

- 로컬 전체 테스트 707개가 통과했다.
- 서버에 올린 파일 조합으로 관련 테스트 120개가 통과했다.
- 2026-11-07 15:13(서버 시각)에 배포했다. 서비스 active, Discord Gateway 연결을 확인했다.
- 서버에서 도구 호출을 직접 실행해 봤다. 진행 기록이 남고 `⏳ 작업 중 · 5초 / … 웹 검색`으로 표시되는 것을 확인했다.
- 실제 Discord 요청에서 메시지가 고쳐 써지는 모습은 보지 않았다. 소유자 계정으로 메시지를 보내야 확인할 수 있다.

## 아직 모르는 것

- 모델이 도구 없이 오래 생각하는 동안에는 "요청을 이해하는 중"과 경과 시간만 보인다.

## 셀프 인터뷰

1. **왜 인자는 진행 표시에 넣지 않았나요?** 채널에 카톡 받는 사람이나 메시지 원문이 보일 수 있어서입니다. 도구 이름만으로도 지금 어느 단계인지는 알 수 있습니다.
2. **편집이 너무 잦으면 Discord 제한에 걸리지 않나요?** 단계가 바뀔 때만 고쳐 쓰고 확인 간격도 2초라서, 메시지 하나를 5초에 5번 넘게 고치는 경우는 생기지 않습니다.
3. **상태 메시지가 실패하면 답을 못 받나요?** 아닙니다. 보내기나 마지막 고쳐 쓰기가 실패하면 상태 메시지를 지우고 기존 방식으로 새 메시지를 보냅니다.

## 이어서: 검색은 끝났는데 실패로 답한 문제

진행 표시를 배포하고 난 뒤 첫 휴대폰 검색 요청(15:19)이 결과 화면까지 갔다. 그런데 답은 "작업 단계·시간 제한 또는 도구 오류로 완료하지 못했습니다"였다. 표시된 숫자는 모델 호출 12회, 도구 13회, 75.9초였다.

- 원인: Hermes 실행기의 모델 호출 한도가 12회(`max_iterations=12`)였다. 휴대폰 작업은 화면 확인과 조작이 짝으로 붙어서 단계를 빨리 쓴다. 한도에 닿으면 Hermes는 모델에게 요약을 요청한다. 그런데 결과가 `completed=false`로 표시돼서 게이트웨이가 그 요약을 버리고 일반 실패 문구를 보여줬다.
- 바꾼 것:
  - 모델 호출 한도: 12회에서 20회로 올렸다. 상수는 `deploy/hermes_policy.py`의 `MAX_ITERATIONS`다.
  - 실행 시간: 실행 예산 120초를 150초로, 프로세스 제한 180초를 210초로, 소유자 요청 권한(lease) 175초를 205초로 늘렸다.
  - 입력 토큰 상한: 60,000에서 100,000으로 올렸다. 호출이 늘어나면 매 호출마다 누적 대화가 다시 들어가기 때문이다.
  - 한도 도달 표시: 한도에 닿은 경우를 `iteration_limit`으로 따로 표시한다. 모델 요약이 있으면 "⚠️ 단계 한도에 도달해 여기까지 정리했어요." 아래에 요약을 그대로 보여준다.
- 확인한 것:
  - 로컬 전체 테스트 711개가 통과했다.
  - 서버에서는 Hermes 자체 Python으로 정책 값을 읽었다. 결과는 `20`, `100000`, `iteration_limit`였다.
  - 게이트웨이 Python으로 한도 결과를 처리해 보니 요약이 그대로 표시됐다.
  - 15:26에 재시작했고 Discord 연결을 확인했다.
  - 같은 요청을 다시 보내서 확인하지는 않았다.
- 비용: 요청 하나가 쓸 수 있는 모델 호출과 토큰 상한이 약 1.7배로 늘었다. 실제로 늘어나는 양은 한도 근처까지 가는 긴 휴대폰 작업에서만 생긴다.

## 이어서: 조작 한 번에 바뀐 화면까지 돌려준다

호출 한도를 20회로 올려도, 버튼 하나를 누르는 데 모델 호출이 2번 들었다. 조작에 1번, 바뀐 화면을 보는 `android_screen`에 1번이다. 배달 주문은 15~20번쯤 조작해야 하므로 이 방식으로는 호출이 30~40번 필요하다.

- 바꾼 것:
  - `AndroidControl(observe_after=True)`이면 조작 도구 6개(열기, 누르기, 입력, 입력 확정, 스와이프, 뒤로/홈)가 조작한 뒤 1초(앱 열기는 3초) 기다렸다가 화면을 관찰한다. 결과의 `screen`에 그 화면을 담아 돌려준다.
  - 모델에게 보이는 도구 설명과 지침도 바꿨다. "다음 조작은 결과 screen의 snapshot을 쓰고, android_screen은 screen이 없을 때만 부른다."
  - 조작 후 관찰이 실패해도 조작 결과는 그대로 돌려준다. 이때는 `next: android_screen`을 붙여서 모델이 직접 화면을 다시 보게 한다.
  - 8,000자 자르기 예외를 `android_` 도구 전체로 넓혔다. 화면 JSON이 잘리지 않게 하기 위해서다.
  - 카톡 자동응답과 나와의 채팅 흐름은 자체 관찰 순서를 쓰므로, 예전 방식(`observe_after=False`)을 그대로 둔다.
- 확인한 것:
  - 로컬 전체 테스트 716개가 통과했다.
  - 서버에 올린 파일 조합으로 관련 테스트 134개가 통과했다.
  - 15:44에 재시작했고 Discord 연결을 확인했다.
  - 서버의 실제 안드로이드에서 배민 열기, 위로 스와이프, 뒤로 가기를 각각 한 번씩 실행했다. 세 조작 모두 화면을 같이 돌려줬다. 노드 수는 102, 118, 100개였고 걸린 시간은 5.2초, 5.2초, 2.5초였다.
- 아직 모르는 것:
  - 실제 Discord 요청에서 모델이 `android_screen`을 덜 부르는지는 아직 보지 못했다.
  - 1초 대기가 모든 화면 전환에 충분한지 모른다. 부족하면 바뀌기 전 화면이 돌아올 수 있다. 그래도 snapshot 검증 때문에 잘못된 요소를 누르지는 않고 오류로 끝난다.

## 이어서: 배민 검색 결과가 "전송 결과를 확인하지 못했습니다"로 바뀐 문제

15:49 요청 "초밥 먹고싶은데 연 초밥집이랑 2만5천원 이하 메뉴 정리해줘"는 모델 호출 18회, 125.5초를 쓰고도 답이 "전송 결과를 확인하지 못했습니다." 한 줄로 끝났다. 스크린샷도 붙지 않았다.

- 원인: 작업 실행기는 도구 인자나 결과에 `kakao`라는 글자가 한 번이라도 나오면 카톡을 사용한 것으로 판정했다. 카톡을 사용했다고 판정되면 게이트웨이는 개인정보 보호를 위해 답을 카톡 결과 코드로 바꾸고 스크린샷을 지운다. 배민 가게나 결제 화면에는 카카오페이 같은 문구가 들어 있어서 이 판정에 걸린 것으로 보인다. 같은 경로를 다시 열어 그 문구를 직접 찾지는 못했다.
- 바꾼 것:
  - 카톡 사용 판정(`kakao_activity`)은 이제 세 경우에만 켜진다: 카톡 도구(이름에 `kakao`가 들어감), `app=kakao`로 앱을 연 경우, 화면에 카톡 앱 패키지(`com.kakao.talk`)가 있는 경우.
  - 같은 질문을 서버에서 다시 돌려 보니, 이번에는 모델이 배민을 쓰지 않고 지역을 되물었다. 그래서 지침을 추가했다: 음식·배달·근처 가게 요청은 지역을 되묻지 말고 배민의 등록된 배달 주소 기준으로 찾는다. 가게는 최대 3곳만 열어 보고, 다 보지 못해도 확인한 곳까지 정리한다.
- 확인한 것:
  - 로컬 전체 테스트 719개가 통과했다.
  - 서버에서 같은 문장으로 Hermes를 직접 실행했다(Discord는 거치지 않음). 영업 중인 초밥집 3곳의 2만 5천 원 이하 메뉴와 가격, 최소주문 금액, 배달팁이 정리돼 나왔다.
  - 그때 측정값: 모델 호출 13회, 도구 12회, 입력 토큰 38.1k, 87.7초. 실패한 요청은 18회, 90.8k, 125.5초였다.
  - 화면 관찰 도구 `android_screen`은 한 번도 따로 부르지 않았다. 조작 결과에 화면이 같이 오는 변경이 효과를 낸 것이다.
  - 측정은 한 번이다.
