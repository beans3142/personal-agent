# 배민 로그아웃을 휴대폰 초기화로 단정하지 않는다

> 2026-11-07 · 읽기 전용 진단 · Android 컨테이너와 앱 설치 정보 각 1회 조회

## 문제와 확인한 근거

배민이 로그인 선택 화면을 보여 주자 기존 로그인 데이터가 초기화된 것인지 확인했다. 실행 중인 서버에서 Android 컨테이너 생성일, 데이터 연결 경로, 배민 설치일을 조회했다. 컨테이너와 앱은 11월 2일에 생성·설치된 것이고, Android `/data`는 기존 호스트 디렉터리에 연결돼 있었다. 앱 데이터 디렉터리도 남아 있었다. 전체 환경이 새로 생성됐다는 근거는 발견하지 못했다.

기존 작업 기록은 배달 주소 보존과 비회원 검색만 검증했으며 계정 로그인 성공은 미확인으로 기록했다. 오늘 별도 점검 기록은 로그인 선택 화면을 확인했다고 적혀 있다. 이 진단에서는 앱을 열거나 화면을 이동하지 않았고 로그인 정보를 읽거나 바꾸지 않았다.

## 남은 불확실성

컨테이너와 앱 데이터 디렉터리가 남아 있다는 사실만으로 개별 로그인 정보가 지워지지 않았음을 증명할 수 없다. 과거 배민 로그인 성공 여부와 이후 세션 만료·해제 원인은 확인되지 않았다. 다음 인증 전후와 재시작 후 계정 화면을 비교해야 로그인 유지 여부를 검증할 수 있다. 매번 재로그인하도록 설계한 환경은 아니다.

## 현재 화면 추가 확인

사용자의 현재 로그인 상태 확인 요청에 따라 실행 중인 기기 작업이 없는지 확인한 뒤 배민을 열고 마이배민 탭을 눌렀다. 카카오·네이버·애플·구글 및 휴대폰번호·이메일 또는 아이디 로그인 선택 화면이 나타나는 것을 직접 확인했다. 확인 시점의 서버 배민 앱은 로그인되지 않은 상태였다. 로그인은 수행하지 않았으며 로그인 선택 화면을 남겨 두었다. 과거 로그인 해제 원인은 이 확인만으로 알 수 없다.

## 셀프 인터뷰

**설치일만으로 초기화를 배제할 수 있나요?**
아닙니다. 앱 데이터 일부가 삭제됐을 가능성은 남습니다.

**사용자의 로그인 기억이 틀렸다고 판단했나요?**
아닙니다. 기록에 검증 근거가 없다는 뜻이지 로그인하지 않았다는 뜻은 아닙니다.

**어떤 검사가 남았나요?**
인증 후 서버 재시작 전후 동일 계정이 유지되는지 확인해야 합니다.

## 휴대폰번호 로그인 시도

사용자가 휴대폰번호 로그인을 요청해 로그인 선택 화면의 해당 항목을 눌렀다. 인증 WebView가 화면 로딩 실패를 표시했다. 화면 재시도 후 흰 화면을 확인했으며 앱 프로세스만 재실행한 뒤 같은 로그인 경로에서도 동일한 로딩 실패가 재현됐다. 앱 데이터 삭제·로그아웃·재설치는 하지 않았다. 개인정보 입력 폼에 도달하지 못했고 문자 인증 요청도 수행하지 않았다. 서버 네트워크, 인증 서비스, WebView 중 어느 요소가 원인인지는 확인하지 못했다. 제공된 개인정보는 코드·일지에 저장하지 않았다.

## 인증 API 연결 오류 추가 진단

Android Chromium 로그에서 회원 인증 화면이 회원 API `/v1/login/own/spec`를 호출할 때 `Access-Control-Allow-Origin`이 없는 응답 때문에 CORS 오류가 발생한 기록을 확인했다. 같은 서버에서 개인정보·인증정보 없이 별도로 요청한 결과 인증 HTML 페이지는 HTTP 200, 회원 API의 GET과 OPTIONS는 모두 HTTP 403이었다. 403 응답의 Server 헤더는 cloudflare였고 허용 Origin 헤더는 없었다. 따라서 해당 서버에서 회원 API 접근이 거절되고, 앱 웹 화면에서는 이를 CORS 오류로 관찰한다는 근거가 있다. 서버 IP 제한, 요청 헤더·인증 요건, 웹 방어 정책 중 정확히 어떤 규칙 때문인지는 확인되지 않았다. 별도 무인증 요청의 403이 실제 앱 요청의 HTTP 상태와 동일하다는 직접 네트워크 캡처는 없다. HTTP 전체 차단, 개인정보 오류, 통신사 오류로 단정하지 않는다. 보안 설정 변경이나 우회는 하지 않았다.

## 실제 앱 응답과 PC 대조로 원인을 좁혔다

추가 분석에서 기존 WebView 디버깅 소켓에 일시적으로 연결하고 사용자가 보던 재시도 버튼을 눌러 실제 네트워크 이벤트를 관찰했다. 실제 앱의 회원 사양 조회 GET 요청에 HTTP 403, 응답 형식 HTML, 서버 헤더 cloudflare가 기록됐다. 이어서 `MissingAllowOriginHeader`와 `net::ERR_FAILED`가 발생했다. 앞 절에서 남겨 둔 실제 앱 HTTP 상태의 불확실성은 이 관찰로 해소했다. 보안 정책이나 앱 설정을 변경하지 않았고, 임시 로컬 전달 포트는 관찰 후 제거했다.

별도 무인증 요청의 거절 HTML 전문에서 읽을 수 있는 안내는 보안 위반 접근 제한과 올바르지 않은 요청이라는 내용이었다. 앞선 짧은 본문 확인은 내장 글꼴 데이터에 가려 안내문을 보지 못했다. 제한된 길이로 전체 문서를 읽고 스타일을 제거해 안내문을 확인했다.

동일한 회원 사양 API, Origin, 일반 User-Agent를 사용한 요청은 현재 Windows PC에서 JSON HTTP 200으로 성공했고 서버에서는 HTML HTTP 403이었다. 이어서 일반 User-Agent와 앱에서 관찰한 WebView User-Agent를 각각 사용해 PC·서버 조합 네 개를 한 번씩 대조했다. PC 두 조합은 모두 200과 허용 Origin 헤더가 있었고 서버 두 조합은 모두 403이며 해당 헤더가 없었다. 이 조회에는 로그인 정보나 개인정보를 보내지 않았다.

확인된 직접 원인은 앱 내부 인증 설정 조회가 보안 접근 거절 응답을 받는 것이다. CORS 오류는 거절 응답에 허용 헤더가 없어서 나타나는 후속 증상이다. 단순 User-Agent 문자열만의 문제와 로그인 선행 요건이라는 설명은 대조 결과와 맞지 않는다. 서버 IP·데이터센터 접속 환경에 따른 제한이 유력하지만 IP 평판, 네트워크 정책, TLS 클라이언트 특성 등 서버 측 판정 기준 중 어느 항목인지까지 분리하지는 못했다. 인증 웹 페이지 자체가 200으로 열리고 실제 앱 API에서도 HTTP 응답이 도착하므로 인터넷 전체 단절이나 단순 TLS 연결 실패라는 설명도 맞지 않는다.

개인정보 입력 및 문자 발송 단계는 여전히 시작하지 않았다. 이번 검사는 로그인 성공이나 서버 앱의 인증 유지까지 검증한 것이 아니다. WebView 업데이트·앱 재설치가 해결책이라는 근거도 확보하지 못했다.

## PC 네트워크 확인과 집 회선 중계 대조

사용자가 공유기 중계를 시험하도록 요청해 PC의 활성 네트워크, 기본 경로, DHCP 정보와 기존 VPN 상태를 읽었다. 유선 인터페이스가 공인 IPv4를 직접 받고 있었고 기본 경로도 공인 주소였다. IGD 대상의 링크 내 SSDP 검색 1회에서는 장비 응답이 없었다. 이는 관리 가능한 가정용 NAT 공유기를 발견하지 못했다는 뜻이며, 물리적 공유기의 부재를 증명하지는 않는다. 브리지 장비나 통신사 제공망일 가능성은 남는다. 공유기 모델과 자체 VPN 지원 여부는 확인되지 않았다.

서버의 루프백 주소에만 임시 SOCKS 중계를 열고 PC의 기존 SSH 연결을 통해 외부로 연결하는 읽기 전용 대조를 했다. IP 조회 서비스에서 중계된 요청의 공인 출구 주소가 PC 직접 조회 주소와 같음을 확인했다. 그러나 회원 사양 API 요청은 서버에서 집 회선을 거쳐도 403이었다. 같은 시점 Windows의 curl과 Python 직접 요청은 각각 200이었다. 후속 대조에서 Windows 직접 IPv4·HTTP/1.1 요청은 200, 집 회선 중계 서버의 HTTP/1.1 요청은 403, 기본 HTTP/2 요청도 403이었다. 각 조건을 한 번씩 검사한 결과이며 지속적인 성공률을 측정한 것은 아니다.

이 결과는 앞선 '서버 IP 제한이 가장 유력하다'는 판단을 약화한다. 집 IP 사용만으로 해결된다는 증거는 없고 클라이언트의 TLS·HTTP 특성, 네트워크 경로 및 보안 판정의 다른 입력도 남아 있다. TLS 지문이 원인이라고 확정한 것은 아니다. 이 중계는 실제 Android 앱에 적용하지 않았으며 로그인이나 문자 인증 요청도 하지 않았다. 임시 중계 프로세스는 각 검사 뒤 종료했고 지속적인 VPN·라우팅·공유기 설정은 변경하지 않았다.

## 카카오 로그인 경로와 동일 계정 여부 확인

사용자가 기존 서버 카카오톡을 통한 배민 로그인을 승인했다. 실행 중인 별도 기기 작업이 없는지 확인한 뒤 배민 로그인 선택 화면에서 카카오 항목을 눌렀다. 초기에 자동 클릭 영역 계산이 화면 전체를 선택해 실제 버튼이 눌리지 않은 사실을 확인했고, 화면에서 관찰한 카카오 버튼 자체의 경계 안을 누른 뒤 다음 화면으로 이동했다. 이 클릭 영역 계산 문제의 전역 코드는 이번에 변경하지 않았다.

정확한 버튼을 누른 뒤 배민은 제목이 회원가입인 SNS 가입 WebView로 이동했고 화면 로딩 실패를 표시했다. 기존 계정 연결, 가입 동의, 개인정보 제출, 문자 발송, 신규 회원 생성은 추가로 진행하지 않았다. 따라서 배민 로그인 성공이나 계정 통합을 확인한 결과는 아니다. 가입 화면으로 이동한 사실만으로 기존 배민 계정과 카카오가 확실히 별개라고 단정하지도 않는다. 앱 재실행·서버 재시작 후 로그인 유지 검사는 로그인에 성공하지 못해 수행하지 않았다.

카카오 공식 로그인 문서의 기존 회원 여부 확인·연동 설명을 대조했다. 카카오 인증과 기존 서비스 회원 연동은 별도이며 서비스가 기존 회원 여부를 판단해 연동 또는 신규 가입을 처리한다. 같은 자연인의 네이버·카카오·휴대폰번호라는 이유만으로 배민 회원 계정, 주문 내역 또는 구독이 자동으로 공유된다고 보장할 근거는 확인하지 못했다. 배민의 사용자별 실제 연결 상태는 로그인 후 계정 정보에서 확인해야 한다.

근거: https://developers.kakao.com/docs/ko/kakaologin/common (기존 회원 여부 확인, 연동). 배민 소비자 계정의 동일인 자동 통합 정책을 직접 입증하는 공식 안내는 이번 검색에서 찾지 못했다.

## 로그인 방식 추가 시도 및 카카오 우선 지시

사용자는 네이버·카카오·휴대폰번호 경로를 시도하고 성공 후 유지 여부를 검증하도록 요청했으며, 이어 네이버 설치를 보류하고 카카오를 우선하도록 지시했다. 신규 배민 회원 생성은 승인하지 않은 상태를 유지했다.

네이버 항목을 정확히 누르면 네이버 로그인 SDK의 연결 Activity가 시작된 뒤 원래 로그인 선택 화면으로 돌아왔다. 일반 브라우저와 네이버 앱이 없었으므로 Mozilla 공식 서버의 Firefox 159.0.1 ARM64 APK를 설치했다. 설치 후 Custom Tabs 서비스가 생겼지만 앱 재실행 후에도 네이버 로그인이 진행되지 않았다. 로그에는 Custom Tabs 패키지를 찾지 못한다는 경고가 있었다. 따라서 브라우저 부재만으로 네이버 문제를 전부 설명하거나 해결했다고 쓰지 않는다. 네이버 앱 자체는 이후 우선순위 변경에 따라 설치하지 않았다.

카카오 경로를 다시 선택한 뒤 배민 회원가입 화면의 재시도 요청을 네트워크 이벤트로 관찰했다. 실제 `member.baemin.com/registration/sns` GET과 favicon GET 모두 cloudflare 응답 헤더의 HTTP 403이었다. 앞서 확인한 휴대폰번호 인증 API 실패와는 별개의 실제 페이지 요청 거절이다. 카카오 자체 인증 완료 여부와 배민 기존 회원 매칭 성공은 별도로 확인되지 않았다. 화면의 회원가입 제목만으로 미가입 계정이라고 판단하지 않는다.

같은 Android 기기의 일반 Firefox에서 회원 사양 API를 정상 탐색했을 때 성공 JSON과 통신사·동의 항목 목록이 표시됐다. 이는 서버 전체 인터넷 연결이 막힌 상황과 맞지 않는다. 반면 앱 내부 WebView에서는 403이 관찰되므로 브라우저·클라이언트 환경 차이가 중요하다. WebView 버전은 기존 125였지만 버전 자체가 직접 원인임을 입증하거나 시스템 WebView를 업데이트한 것은 아니다.

진단용으로 현재 관찰된 회원 페이지 주소를 일반 Firefox에서 열었다. 임의 로그인 정보나 토큰을 추출·주입하지 않았으며 주소의 허용된 플래그 외 예상하지 않은 값이 있으면 중단하도록 했다. 페이지는 회원용 별도 웹 주소로 이동했지만 로그인·인증 입력 양식이 표시되지 않았다. 성공 API 조회 또는 브라우저 페이지 탐색을 앱 로그인 성공으로 간주하지 않는다. 화면 진단 출력에 나타날 수 있는 세션 식별값은 이후 출력에서 가렸고 공개 기록에는 포함하지 않았다.

Firefox 최초 실행 안내는 진행했고 기본 브라우저 지정은 취소했다. 기존 앱 데이터 삭제, 새 배민 회원 생성, 휴대폰 문자 인증 요청은 수행하지 않았다. 모든 진단용 임시 포트 전달은 종료했다. 로그인에 성공하지 못했으므로 로그인 유지 검사를 위한 서버 재시작은 수행하지 않았다. 현재 장애는 인증번호를 사용자가 제공하지 않아서 발생한 것이 아니다.
