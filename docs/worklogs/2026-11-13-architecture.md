# 아키텍처 그림을 실행 위치와 요청 흐름 중심으로 재구성

> 2026-11-13 · 상세 기술 구조도 교정 · 컴포넌트·API·프로토콜·저장소 관계와 렌더링 확인

## 문제

기존 그림은 노드 아래의 작은 설명과 긴 우회선에 의존했다. 현재 구현과 미구현 LangGraph가 같은 구조에 섞여 있었고, 휴대폰 입구·Claude 대체 경로·PC 실행 위치가 충분히 드러나지 않았다. 사용자는 직접 보면서 다이어그램을 다듬도록 요청했다.

## 1차 변경 — 후속 교정 전

`gen_architecture.py`에서 SVG를 다시 구성했다. 원본 SVG를 직접 고치지 않았다.

- 기기, 상시 중계, 본체, 외부 연결을 네 열로 나눴다.
- AWS 실행 경계와 외부 모델·서비스를 구분하고 휴대폰 입구를 추가했다.
- 일반 요청 경로와 모델을 거치지 않는 경로를 다른 색과 범례로 구분했다.
- 도구 함수 이름의 긴 나열은 README의 도구 지도에 맡기고 기능 묶음으로 표시했다.
- PC 작업 → 중계 → PC 실행 → 중계 첨부 → 본체 결과 처리 → Discord·앱의 반환 흐름을 별도 순서도로 뺐다. 중계에서 Discord에 파일을 바로 보내는 것으로 오인하지 않게 본체 반환 단계를 명시했다.
- 미구현 LangGraph와 확인하지 않은 상시 호스트 인스턴스 종류 표기를 제거했다.
- README의 중복 개요 Mermaid는 없애고, 요청 순서·도구 지도는 유지했다. 결제만 승인하는 현재 코드와 어긋난 설명 및 오래된 제한 수치도 맞췄다.

## 1차 시각 검토

Python Playwright의 Chromium으로 SVG를 실제 렌더링하고 화면 이미지를 열어 확인했다. 첫 초안에서 본체 배경에 화살표가 가려지고 작은 카드의 아래 여백이 부족한 것을 발견해 레이어 순서와 간격을 수정했다. 이후 PC 반환 단계도 보강했다.

최종본은 1600px 원본과 960px README 폭으로 각각 렌더링했다. `check_architecture.py`는 실제 글자 bounding box를 읽어 카드 내부 여백, 캔버스 잘림, 글자끼리 겹침, 연결선의 카드 통과를 검사한다. 최종 카드 23개·텍스트 93개에서 발견된 문제는 0개였다. 이는 정의된 기하 검사 결과이며 모든 시각적 품질을 자동으로 보증한다는 뜻은 아니다.

README에 남은 두 Mermaid도 Mermaid 11.4.1로 실제 렌더링에 성공했다. 서비스나 도구 실행 코드는 바꾸지 않아 전체 실행 테스트를 반복하지 않았다.

## 아직 확인하지 않은 것

GitHub 서버가 SVG를 처리한 이후의 모든 브라우저·폰트 조합을 확인한 것은 아니다. README에 가까운 폭에서 Windows Chromium 기본 한글 글꼴로 확인했다. SVG는 확대해 볼 수 있다.

## 셀프 인터뷰

**왜 도구별 이름을 줄였나요?**
전체 구성 그림과 MCP 도구 지도에 같은 긴 목록을 반복하면 글자가 작아집니다. 개요에서는 역할과 실행 위치를 먼저 보여주도록 했습니다.

**왜 별도 PC 순서도가 있나요?**
하나의 개요에 PC 왕복선까지 넣으면 중계·본체·기기 사이 연결선이 다른 내용을 가립니다. 반환 단계를 별도로 보여주는 편이 정확합니다.

**코드 생성만으로 완료 처리했나요?**
아닙니다. 생성된 SVG를 실제 렌더링해 보고 레이어 가림과 아래 여백을 수정한 뒤 다시 확인했습니다.

## 후속 교정: 요약 카드가 아니라 상세 기술 구조도

사용자가 첫 재구성이 기능·연결 정보를 줄였고 한국어 명칭도 어색하다고 지적했다. 기존 컴포넌트와 도구 목록을 빼고 설명 카드로 대체한 방향이 요구와 달랐다. 레이아웃 검사 통과를 정보 충실도의 근거처럼 취급해서도 안 됐다.

이번에는 상세 component/deployment graph로 교체했다.

- `Discord Gateway`, `Request Router`, `HermesRunner`, `PreparedExecutor`, `Hermes Worker`, `MCP Server`를 소스와 대응시켰다. `소유자 관문` 등 임의 번역은 제거했다.
- 12개 MCP 도구 모듈의 실제 tool API와 소스 파일을 복원했다. 설명 문장 대신 식별자를 쓴다.
- Relay API, Queue/Registry, Attachment Store, Memory/Conversation/Schedule/Device 저장소를 표시했다.
- HTTPS, Discord Gateway/REST, MCP stdio, SQLite, 파일 IPC와 PC 엔드포인트를 연결선·data flow에 표시했다.
- Windows의 Desktop App·Whisper·TTS·Agent, 본체의 스케줄러·상태 점검·유휴 종료와 승인 처리를 다시 분리했다.
- 코드 대조 중 Device Tools가 Device Node API를 호출하는 것처럼 보이던 연결을 같은 Device Registry에 접근하는 관계로 고쳤다. 요청 처리와 worker 준비 관계도 분리했다.

노드와 선의 정의는 규칙대로 `scripts/gen_architecture.py` 안에 유지했다. 중간 편집용 파일은 최종본에 남기지 않았다. 첫 대량 shell 쓰기 명령은 자동 심사에 막혀 변경되지 않았고, 이후 파일 패치로 수정했다.

최종 렌더링은 원본 2240×1660으로 직접 열어 확인했다. 시각 검사기는 새 노드 형식과 실제 글자·아이콘 충돌을 검사하도록 보완했다. 노드 50개·텍스트 168개에서 정의한 검사상 문제는 0개였다. 늘어난 글자는 해설 문장이 아니라 컴포넌트·API·파일·프로토콜 레이블이며, 개수 자체를 품질 지표로 삼지 않는다.

AGENTS.md에도 고도화 시 세부 정보 보존, 표준 용어·코드 식별자 사용, 코드와 연결 의미 대조를 추가했다.

## 후속 교정: 코드 문맥 없이 읽는 역할 중심 구조도

상세 정보를 복원하면서 파일명·함수명·API 경로를 앞세웠다. 사용자는 각 구성 요소가 무엇을 하는지 보여 달라고 요청했다. 코드와 대응되는 이름이라는 이유만으로 처음 읽는 사람에게 설명이 된다고 판단한 것이 잘못이었다. 위 기술 구조도는 중간 결과이며, 현재 README 그림은 이 절의 역할 중심 버전이다.

구성 요소와 연결은 보존하고 표시 문구를 바꿨다. 예를 들어 요청별 실행 관리, 실행 환경 사전 준비, 기기 작업 전달처럼 수행 역할을 제목으로 쓰고, 바로 아래에는 처리 내용을 적었다. 연결선은 호출 식별자 대신 요청·답변, 기억 저장·검색, 작업·실행 결과처럼 주고받는 내용을 표시한다. PC 파일 전달 과정에서도 엔드포인트 대신 요청, 실행, 업로드, 결과 수신, 사용자 전달을 보여 준다. 제품명은 구분에 필요한 곳에 유지했다.

길어진 한글이 연결선과 겹치는 9곳을 첫 렌더링 검사에서 발견해 경로와 문구를 조정했다. 최종 SVG를 Chromium으로 렌더링하고 원본 이미지를 직접 열어 확인했다. 노드 50개와 연결선 개수는 직전 커밋과 동일하다. 실제 글자·아이콘 경계 검사에서 문제 0개였으며, 표시 텍스트의 파일명·함수명·엔드포인트도 별도로 확인했다. 자동 배치 검사와 작성자의 시각 검토는 초독자의 이해도 검증을 대신하지 않는다. 독립적인 독자 시험은 하지 않았다.

README 설명과 AGENTS.md도 역할·전달 정보 중심 원칙으로 맞췄다. 실행 동작은 바꾸지 않았으며 Python 문법 검사와 변경 파일 공백 검사를 수행했다.

**파일명만 지우면 충분한가?** 역할과 처리 내용으로 대체하고 선에도 전달 내용을 표시해야 한다.

**정보를 줄인 것은 아닌가?** 기존 구성 요소와 연결을 유지하고 화면의 이름을 바꿨다.
