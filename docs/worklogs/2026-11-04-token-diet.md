# 도구 설명이 토큰을 먹고 있었다

> 2026-11-04 · `bench/token-experiments` 브랜치 `2eb40f0` `ea72368` · 요청 20개 기준 호출 1회당 입력이 64,474에서 12,693토큰으로 80% 줄었다(오프라인 측정)

## 무엇이 문제였나

"1달러는 몇 센트야?" 같은 짧은 질문에도 모델 입력이 3천 토큰을 넘었다. 요금이 따로 나가지 않는 구독 모델이지만 사용 한도는 정해져 있어서 한도를 어디에 쓰고 있는지부터 알아야 했다.

## 왜 그런 일이 생겼나

요청 하나를 처리할 때 모델에는 사용자 문장만 가지 않는다. 시스템 지시문과 도구 24개의 설명이 매번 같이 간다. 토크나이저(`o200k_base`)로 세어 보니 도구 설명이 2,371토큰, 지시문이 840토큰이었고 사용자 문장은 평균 13토큰이었다.

## 고를 수 있던 방법

| 방법 | 결과 | 판단 |
| --- | --- | --- |
| 요청에 필요한 도구 묶음만 보내기 | -63% | 적용 |
| 도구 설명을 첫 문장만 남기기 | 추가 -2%p | 모델이 도구를 잘못 고를 위험이 더 커서 보류 |
| 정해진 문장은 코드가 처리하고, 같은 질문은 저장한 답 재사용 | 누적 -80% | 적용 |
| 작은 로컬 모델(Ollama)로 분류 | 측정 안 함 | 4GB ARM CPU에서 느리고 메모리를 많이 먹어서 제외 |

## 바꾼 것

비교 기준이 흔들리지 않게 실제로 쓸 요청 20개를 유형별로 고정했다(단순 질문, 고정 명령, 도구 하나, 여러 단계, 앱 조작). 도구는 운영 코드의 이름과 입력 형식을 그대로 쓰고 결과만 가짜로 돌려줘서 실험 중에 메시지가 실제로 나가지 않게 했다(`bench/stubs.py`).

처음에는 실제 모델을 부르며 비교하려 했지만 방향을 바꿨다. 구독 모델을 실험 목적으로 수백 번 자동 호출하는 것은 일반 사용 범위를 벗어날 수 있었다. 모델을 부르지 않고 토크나이저로 입력 크기만 계산하는 오프라인 측정(`bench/measure.py`)으로 좁혔다.

## 확인한 것

| 방식 | 입력 토큰 | 기준 대비 |
| --- | ---: | ---: |
| 기준 (도구 24개 전부) | 64,474 | - |
| 필요한 도구 묶음만 | 23,792 | -63.1% |
| + 설명 첫 문장만 | 22,522 | -65.1% |
| + 코드 라우터와 답변 캐시 | 12,693 | -80.3% |

코드 라우터가 20개 중 8개, 답변 캐시가 1개를 모델 없이 처리했다.

## 틀린 지점

도구 고르기 첫 버전은 "알려줘"만 들어 있어도 예약 도구를 붙였다. "파이썬 리스트 뒤집는 방법 알려줘"에 예약 도구가 따라붙어 테스트가 실패했다. 한국어에서 "알려줘"는 예약보다 질문에 훨씬 자주 쓰인다. "10분 뒤", "알림" 같은 시간 표현이 있어야 예약으로 보도록 조건을 좁혔다.

## 아직 모르는 것

- 호출 1회당 입력만 셌다. 실제 요청은 모델을 여러 번 부르고 도구 결과도 쌓이므로 실제 절감 비율은 다를 수 있다.
- 요청 세트를 직접 만들었으니 라우터가 처리한 9개는 낙관적인 수치다.
- 필요한 도구를 빠뜨리면 모델이 일을 못 한다. 그때 전체 도구로 다시 시도하는 장치와 비용을 따로 재야 한다.

## 셀프 인터뷰

**왜 모델 교체가 아니라 입력 줄이기부터 봤나요?**
측정해 보니 입력의 대부분이 요청과 무관한 도구 설명이었습니다. 모델을 바꿔도 이 구조는 그대로라서 구조부터 고치는 쪽이 효과가 컸습니다.

**실제 모델로 실험하지 않은 이유는요?**
구독 모델을 실험 목적으로 대량 자동 호출하면 일반 사용 범위를 벗어날 수 있었습니다. 대신 모델 없이 계산할 수 있는 입력 크기와, 모델 없이 처리되는 요청 수를 쟀습니다. 결과 품질은 운영 답장에 찍히는 토큰 기록으로 확인할 계획입니다.

**가장 크게 배운 점은요?**
고정된 요청 세트로 한 번에 하나씩 바꾸며 재야 무엇이 효과가 있었는지 설명할 수 있다는 점입니다. "알려줘" 오분류도 테스트를 먼저 만들어 둔 덕분에 바로 잡혔습니다.
