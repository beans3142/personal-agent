# 속도 개선 A/B 2~4단계: 직접 답변, 사전 준비, 캐시 묶음

> 2026-11-13 · 공개 테스트 1,027개 통과(환경 전용 1개 제외) · A/B 결과에 따라 두 변경 적용, 캐시 묶음 강화는 비활성 유지

## 진행 기준

사용자는 개선을 하나씩 적용하며 A/B로 절감 효과를 확인하도록 요청했다. 1단계 요청 전달 대기는 별도 글에 있다. 이번에는 요청 전달 변경을 고정한 상태에서 각 후보를 분리해 시험했다. 모델 호출 시험은 임시 대화 기록·첨부 경로를 사용했으며 Discord나 카톡으로 시험 내용을 보내지 않았다.

## 2단계: 시간·날짜·요일은 직접 답하기

`simple_reply`가 엄격히 일치하는 읽기 질문만 처리한다. 다른 작업이 섞이거나 외국 시각·내일 일정 등을 묻는 문장은 기존 경로로 보낸다. 현재 시각은 매 요청 새로 읽으며 답변을 캐시하지 않는다. 본체의 Gateway와 상시 중계의 음성 규칙에서 함께 사용한다. 기존 PC·폰·서버 전원 규칙은 이미 있으므로 중복 구현하지 않았다.

같은 세 질문(현재 시각, 오늘 날짜, 오늘 요일)에 A/B 순서를 번갈아 적용했다. A는 기존 Hermes 경로, B는 직접 처리다. 동일한 임시 Gateway 경로에서 측정했고 실제 서비스의 웹 QuickLane 우회나 네트워크·음성 출력 시간은 포함하지 않는다.

| 방식 | 표본 | 평균 서버 처리 | 모델 호출 합계 | 답 검증 |
| --- | --- | --- | --- | --- |
| A 기존 | 3 | 19,162.75ms | 9 | 3/3 |
| B 직접 처리 | 3 | 5.75ms | 0 | 3/3 |

단 세 종류의 정형 질문에 대한 결과다. 임의의 사용자 질문이 빨라진다는 뜻이 아니다. `DAEVIS_SIMPLE_REPLIES=off`로 이전 경로와 다시 비교할 수 있다. 본체와 상시 중계에 적용했다.

## 3단계: 단일 사용 실행부 사전 준비

기존에는 요청 후 Hermes 모듈을 로딩했다. 이제 모듈만 읽은 프로세스 하나를 대기시킬 수 있다. 대기 프로세스에는 활성 요청 권한·요청 텍스트·첨부 경로를 주지 않는다. 요청을 받는 순간 환경을 완전히 교체하고, 한 요청을 처리하면 그 프로세스를 종료한다. 이후 다음 대기 프로세스를 만든다. 대화 객체나 실행 권한을 요청 간 재사용하지 않는다.

MCP 연결은 계속 요청마다 새로 만든다. 연결은 요청별 도구 허용 목록과 권한 환경을 캡처하므로, 이 부분까지 공유하는 방식은 이번에 넣지 않았다. 약 2.5초의 기존 연결 측정값을 절감했다고 주장하지 않는다.

실제 운영 본체에서 모델이나 MCP를 호출하지 않는 시작 전용 probe를 A/B 각각 3번 실행했다. B가 대기 상태가 될 때까지 준비한 뒤 요청 시점부터 측정했다.

| 방식 | 표본 | 요청 후 평균 시작 시간 | 별도 비용 |
| --- | --- | --- | --- |
| A 새 프로세스 | 3 | 2,550.55ms | 요청 시 import |
| B 사전 준비 | 3 | 318.32ms | 미리 약 2.2초 준비, 약 95MB RSS 유지 |

요청 이후 대기 차이는 약 2.23초다. 전체 CPU 작업을 없앤 것이 아니라 유휴 시간으로 옮긴 것이다. 준비 프로세스는 하나로 제한한다. 시작 실패 전에는 기존 cold 경로로 돌아가지만, 요청을 넘긴 이후 오류나 시간 초과에는 재실행하지 않는다.

실제 모델 호출 smoke에서도 준비 완료, 준비 실행부 사용 1회, 정답, 모델 1회·도구 0회를 확인했다. `DAEVIS_PREPARED_WORKER=on`으로 적용했다. 프로세스 제목을 대기 중에는 `daevis-prepared (idle)`, 요청 중에는 `hermes-worker.py (prepared active)`로 설정해 기존 worker 점검 명령이 활성 요청을 계속 감지하게 했다.

Hermes가 다른 관리 인터프리터로 재실행하는 점을 발견했다. `setproctitle`은 설정된 인터프리터뿐 아니라 재실행 대상에도 필요하다. requirements 파일에 버전을 남겼다. 의존성이 사라져 대기 시작에 실패하면 요청 전달 전 cold 경로로 되돌아간다.

## 4단계: 반복 입력 캐시 묶음 비교

Hermes 자체에 입력 캐시 기능과 사용량 보고가 이미 있다. 새 응답 캐시를 만들지 않았다. A는 기존 동작, B는 계정·채널·공개 여부·소유자 권한·도구 목록·모델로 나눈 안정적인 해시 키를 Hermes의 `gateway_session_key`에 제공한다. 이 키는 권한이나 대화 기록이 아니며, 매 요청의 MCP 권한은 여전히 새로 검증된다.

같은 고정 지시와 짧은 요청을 A/B/A/B 순서로 두 차례, 총 8회 호출했다. 사전 준비는 양쪽 모두 끄고 나머지 조건을 맞췄다. 공급자 자동 캐시를 끈 시험이 아니라 기존 키 방식과 안정 키 방식의 비교다.

| 방식 | 표본 | 평균 응답 | 입력 캐시 적중 | 캐시 읽기 토큰 합계 | 답 검증 |
| --- | --- | --- | --- | --- | --- |
| A 기존 | 4 | 9,375.33ms | 1/4 | 1,664 | 4/4 |
| B 안정 키 | 4 | 9,832.22ms | 1/4 | 5,888 | 4/4 |

B의 한 번 적중에서 더 많은 입력을 재사용했으나 일관되지 않았고 속도 개선 증거도 없다. 작은 표본으로 일반적인 캐시 적중률이나 요금 절감을 추정하지 않는다. `DAEVIS_PROMPT_CACHE=off`를 유지했다. 기존 공급자 자동 캐시는 그대로 동작한다. 비교 기능과 캐시 사용량 수집은 남겨 후속 검증을 재현할 수 있게 했다.

## 검증과 한계

- 관련 집중 테스트 201개 통과.
- 공개 테스트 1,027개 통과, 기존 Windows→bash 경로 문제 테스트 1개 제외. 이번 변경과 무관한 환경 전용 제외다.
- 시험 전 소유자 worker를 확인했다. 한 점검 명령에서는 파일 경로 문자열 때문에 자기 자신을 busy로 잡았고, 확인 명령을 분리해 바로잡았다.
- 운영 두 서비스 active 및 본체 대기 실행부 하나를 확인했다.
- 실제 음성의 시작부터 답을 듣기까지 시간을 A/B 측정한 것은 아니다. 단계별 숫자를 단순 합쳐 전체 절감량으로 주장하지 않는다.

## 셀프 인터뷰

**왜 카톡 전송도 바로 처리하지 않았나요?**
이미 일부 직접 경로가 있습니다. 이번 정형 처리 확대는 시각·날짜처럼 읽기만 하는 정확한 문장으로 제한했습니다.

**세션 유지와 같은 건가요?**
요청의 대화나 권한을 유지하는 세션 공유가 아니라 무거운 import만 미리 끝낸 실행부를 유지하는 방식입니다.

**캐시 기능을 만들었는데 왜 끄나요?**
A/B에서 안정적인 이득을 확인하지 못했기 때문입니다. 기존 자동 기능과 중복해 켜는 것 자체를 성과로 보지 않습니다.
