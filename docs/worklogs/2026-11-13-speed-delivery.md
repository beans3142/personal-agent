# 요청 전달 대기 개선: 1단계

> 2026-11-13 · 로컬 통제 시험 각 8회: 평균 전달 대기 1,030.05ms → 75.46ms

## 순서와 기준

사용자는 전달 대기, 단순 요청 처리, 실행부·연결 재사용, 반복 입력 캐싱을 하나씩 적용하며 절감 효과를 찾도록 요청했다. 이번 단계는 본체 서버의 음성 요청 수신에만 한정한다. 다음 단계 후보는 정형 요청의 모델 우회, 요청별 권한을 분리한 실행부 재사용, 고정 입력 캐시다. 이번 커밋에 이들을 함께 넣지 않는다.

## 문제와 변경

기존 `agent_loop`는 중계 서버를 조회한 뒤 매번 2초 쉬었다. 요청이 그 직후 도착하면 다음 조회까지 기다렸다. `/agent/poll`을 추가해 본체가 최대 20초 연결을 유지하고 중계 서버가 150ms 간격으로 새 요청을 확인해 돌려주도록 바꿨다. 기존 `/poll`은 이전 클라이언트용으로 유지한다.

이 경로는 등록된 `agent-main` 인증만 허용한다. 결과와 중복 방지 방식은 바꾸지 않았다. 기존 요청을 재시도하는 기능은 추가하지 않았다. 요청 없는 상태에서 즉시 빈 응답을 반복하지 않도록 서버 대기를 사용하며 클라이언트 제한 시간은 35초로 설정했다.

## 측정

`scripts/benchmark_agent_delivery.py --trials 8`로 실제 SQLite registry를 사용했다. 기존 수신기와 새 수신기에 각각 8개의 동일한 도착 위상(초기 확인 후 0.1~1.85초)을 사용했다. 임시 registry만 쓰며 모델이나 실제 사용자 기기를 호출하지 않는다.

- 기존: 평균 1,030.05ms, 최대 1,905.24ms
- 변경: 평균 75.46ms, 최대 143.87ms
- 이 시험의 평균 차이: 954.59ms (약 92.7%)

로컬 시험이며 네트워크, 본체 부팅, 모델 응답, 도구 실행, 답변 수신 단계는 포함하지 않는다. 전체 47~62초 요청이 같은 비율로 빨라진다는 의미가 아니다. 중계 내부 SQLite 확인 횟수는 늘어나므로 운영 호스트의 부하도 확인해야 한다.

## 검증 기준

인증 없는 호출·PC 자격으로 호출·잘못된 대기 값 거절, 대기 중 도착한 요청 수신, 동일 작업을 두 번 전달하지 않는 동작을 회귀 테스트로 확인한다. 운영 적용은 중계부터 하고 본체 수신기를 뒤에 바꾼다. 소유자 worker가 실행 중이면 재시작하지 않는다.

## 셀프 인터뷰

**왜 캐시부터 넣지 않았나요?**
이 구간은 매 요청에 들어가는 대기이고 별도 모델 호출 없이 같은 조건에서 비교할 수 있습니다.

**long-poll인데 내부에서 왜 다시 확인하나요?**
기존 SQLite 작업 전달 방식을 유지한 작은 변경입니다. 150ms 확인 비용과 전달 지연을 바꾼 것이며 이벤트 기반으로 완전히 바꿨다고 주장하지 않습니다.

**절감 효과의 범위는요?**
중계에 작업을 넣은 시점부터 수신기가 가져간 시점까지입니다. 사용자 전체 체감은 별도 측정이 필요합니다.

## 운영 적용 결과

관련 테스트 119개가 통과했다. 수정 전 운영 소스와 HEAD 해시가 같은 것을 확인한 뒤 백업했다. 소유자 worker가 없고 중계에 유효한 queued/dispatched 음성 작업이 없는 것을 확인했다. 중계에 먼저 배포하고 active를 확인한 뒤 본체를 재시작했다.

운영 중계 호스트에서도 독립된 임시 registry로 같은 시험을 각 8회 실행했다.

- 기존: 평균 1,031.56ms, 최대 1,906.64ms
- 변경: 평균 88.52ms, 최대 159.33ms
- 이 시험의 평균 차이: 943.04ms (약 91.4%)

이는 운영 호스트에서 한 통제 시험이며 실제 소유자 요청의 끝까지 응답 시간을 측정한 것은 아니다. 카톡 등 실제 작업은 보내지 않았다. 본체와 중계 서비스는 active를 확인했다.
