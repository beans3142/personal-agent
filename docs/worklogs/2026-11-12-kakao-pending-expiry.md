# 미확인 카톡 전송 기록이 새 요청을 무기한 막던 문제

> 2026-11-12 · 관련 테스트 84개 통과, 운영 서버의 오래된 pending 기록 1건 정리

## 무엇이 문제였나

11월 10일에 남은 직접 전송 pending 기록 때문에 11월 12일의 새 요청도 차단됐다. 서버에서 기록 수정 시각과 status를 확인했다. 당시 실행 중인 Hermes worker와 전송 잠금 파일은 없었다.

## 원인과 바꾼 것

`send_once`가 pending을 발견하면 경과 시간과 관계없이 차단했다. `expire_direct_pending`을 추가해 새 전송이 잠금을 획득한 뒤 120초가 지난 pending은 `expired_uncertain`으로 정리한다. 기존 기록은 파일 수정 시각을 사용하고 새 기록은 시작 시각을 저장한다.

정리할 때 이전 요청 해시를 중복 방지 목록에 보존한다. 따라서 같은 요청의 재시도는 차단하고 다른 새 요청은 진행할 수 있다. 시간 경과를 전송 성공이나 실패로 간주하지 않는다. 자동 재전송도 하지 않는다.

기존 수동 잠금 해제만 유지하는 방법은 매번 사용자 확인을 요구하므로 이번 문제를 해결하지 못한다. 단순 기록 삭제는 중복 방지 근거를 버리므로 택하지 않았다.

## 확인한 것

새 회귀 테스트 두 개가 수정 전 실패하고 수정 후 통과했다. 카톡 감시·나와의 채팅·대상 선택·gateway 테스트 84개가 통과했다. 운영 소스가 수정 전 HEAD와 같은 해시임을 확인하고 백업한 뒤 적용했다. 실행 중인 worker가 없는 것을 확인하고 기존 기록을 정리했다. 결과는 `expired_uncertain`이고 서비스는 active다.

## 남은 범위

실제 카톡 발송 여부는 이번에 확인하지 않았고 메시지도 보내지 않았다. 이 수정은 끝난 작업이 남긴 pending 기록에 대한 것이다. 실행 중인 프로세스의 강제 종료나 프로세스가 남긴 별도 lock 파일 회수는 추가하지 않았다. 만료 정리는 주기 작업이 아니라 다음 전송 시점에 실행된다. 릴스 요청이 도구를 사용하지 않은 문제는 별도 원인 조사가 필요하다.

## 셀프 인터뷰

**왜 120초인가요?**
기존 전송 단계의 60초 마감보다 여유를 주면서 며칠간 차단되는 일을 막는 정책값입니다. 실측 최적값으로 주장하지 않습니다.

**시간이 지나면 성공 처리해도 되나요?**
아닙니다. 결과 미확인 종료로 보존합니다.

**재발 방지는 어떻게 검증했나요?**
오래된 pending 뒤 새 요청은 진행하고 이전 요청은 재전송하지 않는 두 경우를 테스트했습니다.
