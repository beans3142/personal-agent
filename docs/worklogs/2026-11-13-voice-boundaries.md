# 호출어 앞부분과 짧은 문장 중간 쉼 보존

> 2026-11-13 · 음성·데스크톱 관련 테스트 101개 통과

## 문제와 변경

사용자는 호출어가 일부 인식되기 시작했지만 안정성을 조금 더 높이길 원했다. 기존 문장 검출은 시작 직전 약 150ms만 보존했고 600ms의 침묵으로 문장을 종료했다. 합성 입력에서 조용한 첫 음절 240ms 중 절반을 잃는 경우와, 660ms 쉼 때문에 한 요청이 둘로 나뉘는 경우를 재현했다.

시작 전 보존 구간을 360ms로 늘리고 종료 침묵을 800ms로 늘렸다. 호출어 철자 허용 범위, 인식 모델, 실행 조건은 변경하지 않았다. 문장 종료 판정은 설정상 약 200ms 늦어지는 대가가 있다.

## 확인

새 회귀 테스트 두 개는 수정 전 실패하고 수정 후 통과했다. 관련 테스트 101개가 통과했다. 실제 사용자 목소리의 성공률 향상은 아직 측정하지 않았다.

## 속도와 세션 재사용 조사

사용자는 속도·세션 유지·캐싱 가능 부분도 요청했다. 코드를 확인하니 PC 음성 모델은 이미 메모리에 유지하고, 브라우저 세션 및 대화 기록 저장도 구현되어 있다. 반면 Hermes 실행 프로세스와 MCP 연결은 요청마다 생성한다.

소유자 worker가 없는 것을 확인한 운영 서버에서 모델 호출 없이 한 번씩 측정했다. Hermes import는 2.23초, 읽기 도구 4개를 발견하는 MCP 연결은 2.5초였다. 두 측정은 각각 별도 프로세스의 단일 표본이고 전체 요청 지연 감소율로 일반화하지 않는다. 운영 전체 도구 연결과 동일하다고 주장하지 않는다.

실행부 재사용은 후보지만 요청마다 달라지는 소유자 권한, 만료 시각, 대화 범위, 첨부 경로를 분리하는 검증이 필요하다. 답변·전송 결과·UI 화면 캐시는 도입하지 않았다. 입력 프롬프트 캐시의 실제 제공 여부나 적중률도 확인하지 않았다. 요청 전달의 1~2초 폴링과 정형 요청의 모델 우회를 먼저 검토할 수 있다.

## 셀프 인터뷰

**문턱을 낮추거나 비슷한 호출어를 더 허용하면 안 되나요?**
이번에는 정상 말소리까지 호출로 오인할 범위를 넓히지 않고 입력 구간 보존만 조정했습니다.

**속도 개선과 충돌하지 않나요?**
종료 침묵을 200ms 늘리는 것은 지연을 조금 늘립니다. 호출 실패로 반복하는 부담과의 교환이며 실제 성공률은 추가 측정해야 합니다.

**세션 유지로 1분 대기를 없앨 수 있나요?**
측정한 시작 비용만으로는 그렇게 주장할 수 없습니다. 모델 응답과 도구 실행 등 나머지 구간도 측정해야 합니다.
