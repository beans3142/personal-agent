대비스 구조와 설계 판단

Discord로 한마디 하면 서버가 내 계정으로 메일, 지도, 카카오톡, 배달 앱을 다루는 개인 Agent다. 이 문서는 지금 구조가 어떻게 생겼는지보다 왜 이렇게 됐는지를 남기려고 썼다. 무엇을 만들다 어디서 막혔고, 그때 무엇을 고르고 무엇을 버렸는지를 기록했다. 수치는 운영 로그와 실측값이고, 확인하지 못한 것은 확인하지 못했다고 적었다. 2026-11-04 기준이다.

1. 지키기로 한 원칙

처음부터 정해 둔 조건과 만들면서 생긴 규칙이다. 아래 결정들은 대부분 이 네 가지가 서로 부딪히는 지점에서 나왔다.

서버에서, 내 계정으로

PC가 꺼져 있어도 돈다. 메일과 카톡은 봇이 아니라 내 계정으로 나간다. 사람은 휴대폰 승인과 첫 로그인만 한다.

추가 요금 0원

이미 내는 ChatGPT Plus 구독과 AWS 크레딧 안에서만 돌린다. 유료 API 키를 쓰는 기능은 켜지 않는다.

모델보다 코드 먼저

코드로 판단할 수 있는 일은 모델을 부르지 않는다. 구독에도 사용 한도가 있어서 토큰은 줄일수록 오래 쓴다.

애매하면 다시 보내지 않는다

메시지를 보냈는지 확실하지 않으면 재전송하지 않고 멈춰서 알린다. 두 번 보내는 사고가 한 번 못 보내는 것보다 크다.

4. 사흘 동안 바뀐 것

커밋 기록과 인수인계 문서를 날짜순으로 정리했다. 굵은 제목이 그 시점에 부딪힌 문제다.

11-01 밤

Claude Code 세션을 Discord에 잇는 방식으로 시작했다

PC에서 돌고 있는 세션에 메시지를 넘기는 통로였다. PC를 끄면 멈추고, 도구도 기억도 없었다. 이름은 Agent였지만 실제로는 중계기였다.

11-02 00시

직접 짠 Agent 루프를 AWS 서버에 올렸다

게이트웨이, 모델-도구 반복 루프, 기억, 예약을 만들고 ChatGPT 구독 로그인으로 모델을 불렀다. 첫 시험에서 모델이 1회 알림을 1분 반복으로 등록했다. 도구 하나가 두 의미를 갖고 있어서였고, 1회용과 반복용 도구로 나눠 고쳤다.

11-02 01~09시

AWS IP에서 네이버 로그인에 캡차가 떴다

캡차를 뚫는 대신, 서버 브라우저 화면을 휴대폰 링크로 열어 사람이 직접 로그인하게 했다(로그인 포털). Agent는 저장된 세션만 쓴다. 같은 시기에 coupang.com과 yogiyo.co.kr은 AWS IP를 403으로 막았고, 코레일 비공식 라이브러리는 MACRO ERROR로 막혔다.

11-02 오전

카톡과 배민은 웹이 아니라 앱이 필요했다

x86 서버의 Waydroid에서는 Play 화면이 비었고, ARM 서버의 Waydroid는 소프트웨어 렌더러에서 계속 죽었다. Mesa 설정을 바꾸고 다른 이미지도 시험했지만 안정되지 않았다. 공식 ReDroid 13 Docker 이미지로 바꾸고 나서야 앱이 떴다. 이미지는 digest로 고정했다.

11-02 오후

모델이 엉뚱한 버튼을 눌렀다

모델이 화면 노드 번호 대신 목록 순번을 넘겨 런처 앱을 눌렀다. 클릭할 때 노드 ID와 기대하는 버튼 글자를 함께 받아, 둘이 안 맞으면 누르기 전에 실패하게 바꿨다. 이때부터 모든 답장 끝에 처리 시간, 입출력 토큰, 모델·도구 호출 수를 붙였다.

11-02 21시

카톡 입력창이 모델 눈에 안 보였다

태블릿 화면 구조가 약 16,000자인데 공통 도구 결과 제한이 8,000자라, 오른쪽 입력창이 잘려 나갔다. 스크린샷에는 입력창이 있는데 모델은 왼쪽 채팅 목록만 받은 셈이다. 화면 결과는 자르지 않고, 대신 지난 화면은 다음 호출 전에 "교체됨" 표시로 바꿔 입력이 쌓이지 않게 했다.

11-02 22시

"이 문장 보내 줘"에 모델 7번은 과했다

따옴표로 정확한 문장을 준 개인 메시지는 코드가 받는 사람을 확인하고, 입력하고, 한 번 누르고, 새 말풍선이 생겼는지 확인한다. 이미 열린 방 기준 2.5초, 모델 0회였다. 같은 날 방 찾기부터 모델에 맡긴 요청은 20초, 7회 호출, 입력 50.0k 토큰이었다. 단체방 자동응답은 모델 없이 5초마다 화면을 읽고, 새 메시지가 있을 때만 도구 없는 제한된 호출을 한 번 한다(실측 531/116 토큰).

11-02 22시

배포 재시작이 보내던 답장을 끊었다

자동응답이 답을 보내는 도중에 서비스를 재시작했다. 감시기는 다시 보내지 않고 멈췄고, 화면에서 새로 나간 말풍선이 없는지와 입력창에 남은 초안을 확인한 뒤에야 이어서 처리했다. 이후 배포는 감시기를 먼저 비우고 보류 상태가 없는 것을 확인한 다음 재시작한다.

11-02 밤

서버를 계속 켜 두면 크레딧이 빨리 준다

AWS 가격 API 기준으로 두 서버를 30일 내내 켜면 $60.43, ARM 서버만 하루 1시간 켜면 $5.96이다. 쓸 때만 켜는 방식으로 바꿨다. 그러자 꺼진 봇은 Discord 명령을 받을 수 없다는 문제가 생겼다.

11-04 오전

직접 만든 본체와 기존 Agent 프레임워크를 다시 비교했다

Hermes와 OpenClaw 모두 ChatGPT 구독 로그인을 지원한다는 걸 확인했다. 처음에 "요금이 든다"고 걸렀던 판단이 틀렸다. 한국 서비스 도구는 어느 쪽을 쓰든 직접 만들어야 하니, 도구를 MCP 서버로 떼어 내고 본체는 Hermes로 옮기기로 했다. n8n도 이때 설치했다.

11-04 오후

Hermes에서 실제 도구 호출 한 번이 성공했다

처음 지정한 gpt-5.3-codex는 이 계정에서 HTTP 400으로 거부됐다. 계정의 모델 목록을 조회해 gpt-5.6-luna로 바꿨다. MCP memory_search 한 번을 거친 시험은 9.7초, 입력 7,077 / 출력 193 토큰이었다. 비교 실험이 아니라 연결 확인 한 건이다.

11-04 오후

항상 켜진 다른 서버에 전원 봇을 붙였다

이미 상시 운영 중인 작은 서버(daehoon-game)에 81MB짜리 전원 봇을 올렸다. 같은 봇 토큰을 쓰고, 정규식으로만 판단한다. 본체가 켜져 있을 때 두 프로세스가 같은 메시지에 답하지 않도록 본체는 전원 문장을 무시한다.

11-04 오후

토큰이 어디에 쓰이는지 쟀다

요청 20개를 고정해 오프라인으로 쟀다. 도구 설명 24개가 2,371토큰으로 매번 붙고, 요청 문장은 평균 13토큰이었다. 필요한 도구만 보내고 고정 문장을 코드로 처리하자 호출 1회당 입력 합계가 64,474에서 12,693토큰으로 80% 줄었다.

5. 설계 결정 기록

결정마다 그때의 상황, 고른 것, 버린 대안, 그 선택으로 치른 대가를 적었다. 대가까지 적어 두면 나중에 조건이 바뀌었을 때 어느 결정을 다시 열어야 하는지 알 수 있다.

본체는 Hermes, 한국 서비스 도구는 직접 만든 MCP 서버 동작 중

직접 만든 Agent로 갈까, OpenClaw나 Hermes를 쓸까

상황
직접 짠 Agent로 카톡, 지도, 메일까지는 됐다. 그런데 하트비트, 기기 노드, 기억 계층, 스킬처럼 기존 프레임워크에 이미 있는 기능을 하나씩 다시 만들고 있었다. 반대로 서버 Android 카톡, 네이버 로그인 포털, 네이버 지도 경로는 어느 프레임워크에도 없다.
고른 것
경계를 "본체"와 "도구"로 나눴다. 우리가 만든 도구를 MCP 서버 하나로 감싸고, 본체는 Hermes로 옮겼다. Hermes는 Python이라 기존 코드와 언어가 같고, MCP 클라이언트가 있다는 것을 설치 후 실제 연결로 확인했다.
버린 것
OpenClaw는 스킬 생태계와 기기 노드가 강하지만 TypeScript이고, 외부 MCP 서버를 그대로 붙이는지 문서에서 확인하지 못했다. 한 주간 사용기에서 설정 오류로 약 50번 재설치했다는 보고도 있었다. 직접 만든 본체를 계속 키우는 길은 이미 있는 기능을 다시 만드는 비용이 컸다.
대가
Hermes의 일부 기능(이미지 인식, 웹 요약 등)은 구독과 별도로 OpenRouter 요금이 든다. 그래서 Hermes 기본 도구 묶음은 모두 끄고 우리 MCP만 켰다. 결국 Hermes에서 쓰는 것은 대화 루프, 컨텍스트 압축, 작업자 격리 정도다.
이렇게 나눠 두면 본체를 다시 바꿔도 도구는 버리지 않는다. 기존 게이트웨이도 같은 도구 코드를 쓴다.

모델은 Codex OAuth 하나, 웹 채팅 자동화는 넓히지 않는다 동작 중

가진 구독(ChatGPT Plus, Claude Pro, Gemini)을 어떻게 Agent에 쓸까

상황
추가 요금 없이 쓸 수 있는 모델은 이미 내고 있는 구독뿐이다. 간단한 질문은 웹 채팅으로 돌리면 한도를 아낄 수 있다는 아이디어도 있었다.
고른 것
본체 모델은 ChatGPT Plus 로그인(Codex OAuth) 하나로 정했다. Hermes와 OpenClaw 문서 모두 이 방식을 공식 경로로 다룬다. Gemini 웹으로 짧은 질문을 넘기는 기능은 만들어 배포했지만(질문당 10~13초), 더 넓히지 않았고 Hermes 본체에는 연결하지 않았다.
버린 것
Claude Pro는 Anthropic이 외부 도구에서 구독 토큰을 쓰지 말라고 명시해서 붙이지 않았다. ChatGPT 웹 채팅 자동화는 약관에 자동 추출 금지 조항이 있고, 무엇보다 Agent 두뇌와 같은 계정이다. 제재를 받으면 본체까지 같이 멈춘다. 서버에서는 Cloudflare 확인(403)에도 막혔고, 우회하지 않았다.
대가
모든 판단이 한 계정의 한도를 나눠 쓴다. 그래서 다음 결정(코드 먼저)의 비중이 커졌다. 로그인 토큰은 11-10에 만료되어 사람이 한 번 다시 승인해야 한다.

모델 앞에 코드 관문을 겹겹이 둔다 일부 동작 중

구독 한도 안에서 오래 쓰려면 무엇을 줄여야 할까

상황
초기 구조는 모든 요청이 모델을 2~4번 불렀다. 경로 검색 같은 정해진 요청도 마찬가지였다. 측정해 보니 입력의 대부분은 요청과 상관없이 매번 붙는 도구 설명(2,371토큰)과 지시문(840토큰)이었다.
고른 것
모델을 더 싸게 쓰기보다 모델까지 가는 요청을 줄이는 쪽을 골랐다. 전원 문장은 정규식, 고정 문장은 미리 적어 둔 레시피(fixed_plan), 따옴표 메시지 전송은 코드 경로, 단체방 감시는 모델 없는 폴링으로 처리한다. 모델로 가는 요청에는 도구를 4개만 열고, 지난 화면 결과는 압축한다.
버린 것
작은 로컬 모델(Ollama)로 분류하는 방식은 4GB ARM CPU에서 느리고 메모리를 많이 먹어서 뺐다. 도구 설명을 첫 문장만 남기는 방식은 추가 절감이 2%p였고, 모델이 도구를 잘못 고를 위험이 더 컸다.
대가
코드 경로는 문장 모양이 조금만 달라도 안 걸린다. 그래서 안 걸리면 반드시 모델 경로로 넘어가게 했고, 코드 경로가 실패하면 초안을 쓰기 전에만 되돌아간다. 오프라인 측정에서 나온 80%는 요청 세트를 직접 만들어 얻은 낙관적인 수치다.
측정: 요청 20개 기준 호출 1회당 입력 64,474 → 23,792(도구 고르기, -63%) → 12,693(코드 라우터와 답변 캐시 추가, -80%). 상세는 01-token-diet.md.

로그인은 사람이, Agent는 세션만 쓴다 동작 중

서버에서 내 계정으로 로그인하는 일을 누가 할까

상황
AWS IP에서 네이버 비밀번호 로그인은 캡차가 떴고, QR 로그인은 네트워크 오류가 났다. 카톡은 기존 휴대폰에서 보조 기기 승인이 필요했다.
고른 것
서버의 브라우저 화면과 Android 화면을 noVNC로 열고, Cloudflare 임시 터널 링크를 휴대폰으로 보낸다. 사람이 직접 로그인하고 승인하면 세션이 서버에 저장되고, Agent는 그 세션만 다시 쓴다. 링크는 필요할 때만 열고 30분이 지나면 닫는다.
버린 것
캡차 우회, 서버에 가짜 패스키나 가상 인증기 두기, Agent가 비밀번호를 직접 입력하는 방식은 하지 않았다. 계정 보안을 우회하는 방식은 한 번 되더라도 계정 잠금으로 이어질 수 있다.
대가
세션이 만료되면 사람이 다시 들어가야 한다. 지금은 만료를 알려 주는 DM이 없어서 로그에만 남는다. 다음에 붙일 일 1순위다.

앱 작업은 서버 안 Android에서 동작 중

카톡과 배민처럼 앱이 필요한 일을 어디서 돌릴까

상황
카톡은 웹으로 남에게 보낼 수 없고, 배민은 앱 중심이다. "서버에서만 돈다"는 조건이 있다.
고른 것
ARM 서버(t4g.medium) 안에 ReDroid 13 컨테이너를 두고, ADB는 서버 내부 주소로만 열었다. 앱은 uiautomator2로 화면 구조를 읽어 조작한다. 카톡은 태블릿(보조 기기)으로 로그인해서 휴대폰과 같이 쓴다.
버린 것
PC 카톡은 휴대폰과 중복 로그인 문제로 뺐다. Waydroid는 x86과 ARM 양쪽에서 안정되지 않았다. 내 휴대폰을 실행 노드로 쓰는 방식은 앱이 에뮬레이터를 거부할 때의 대안으로 남겨 뒀다. 쿠팡이츠는 사용자 판단으로 뺐다.
대가
4GB 메모리에 Android, n8n, Hermes가 같이 올라가 여유가 약 2GB다. 재부팅 뒤 binder_linux 모듈이 안 올라와 Android가 재시작을 반복한 적이 있어 부팅 자동 적재를 넣었다. Google Play 서비스가 없어서 앱은 공식 설치본을 그대로 옮겨 깔았다.

화면 조작은 "보고, 확인하고, 한 번만" 동작 중

모델이 화면을 잘못 읽거나 잘못 눌렀을 때 피해를 어떻게 막을까

상황
모델이 목록 순번을 노드 ID로 착각해 런처 앱을 눌렀다. 회전 배너 때문에 노드 번호가 밀리기도 했다. 메시지 전송은 되돌릴 수 없다.
고른 것
행동 전에는 반드시 새로 관찰한 화면이 있어야 한다. 클릭은 노드 ID와 기대 글자가 둘 다 맞아야 한다. 마지막 입력 직전에 같은 노드를 다시 찾는다. 성공 판정은 "보냈다"가 아니라 "새 말풍선이 생겼다"로 한다. 같은 오류가 세 번 나면 멈춘다. 결제와 권한 허용 같은 버튼은 주인 DM 승인을 받는다.
버린 것
실패하면 자동으로 다시 시도하는 방식은 버렸다. 보냈는지 모르는 상태에서 재시도하면 같은 말이 두 번 나간다.
대가
애매한 순간마다 멈추고 사람에게 묻는다. 자동응답이 배포 재시작 때 멈춘 것도 이 규칙 때문이었고, 의도한 동작이다.

쓸 때만 켜고, 끄고 켜는 일은 상시 서버가 맡는다 동작 중

크레딧을 아끼면서 Discord 한마디로 켜려면

상황
AWS 크레딧은 정해진 금액이다. 두 서버를 계속 켜면 30일에 $60.43이다. 하지만 서버를 끄면 그 안의 봇도 꺼져서 "켜"라는 말을 못 듣는다.
고른 것
이미 다른 용도로 상시 켜 둔 작은 서버에 전원 전용 봇을 올렸다. 새 AWS 자원은 만들지 않았다. 봇 토큰은 하나만 쓰고 토큰과 주인 ID는 Parameter Store에 SecureString으로 둔다. IAM 정책은 본체 서버 시작·중지와 두 파라미터 읽기만 허용한다. 본체는 요청이 120분 없으면 스스로 끈다. 단, 요청 처리 중이거나 자동응답이 켜져 있거나 예약이 있으면 끄지 않는다.
버린 것
시험용 봇 토큰을 하나 더 만드는 방식은 토큰 하나로 운영하기로 해서 뺐다. Lambda 주소를 휴대폰 단축어로 부르는 방식도 검토했지만, Discord 한마디로 켜는 쪽을 골랐다.
대가
같은 토큰을 두 프로세스가 쓰니, 본체가 전원 문장에 답하면 답이 두 번 나간다. 그래서 본체 게이트웨이가 같은 판별 함수로 전원 문장을 무시한다. 전원 정책은 다른 프로젝트의 CloudFormation 스택 밖에서 붙였기 때문에 그 스택을 갱신하면 사라질 수 있다.
명령은 이름(대비스, 오타 데비스·대비쓰·대빗스·대비즈·ㄷㅂㅅ)과 동작어(온라인·온·켜 / 오프라인·오프·꺼 / 상태·?)가 정확히 맞을 때만 받는다. 문장 중간에 섞인 단어로 서버가 꺼지는 일을 막으려는 것이다.

도구는 읽기부터 조금씩 연다 동작 중

Hermes라는 새 본체에 쓰기 권한을 언제 줄까

상황
MCP stdio는 같은 서버 안의 클라이언트를 믿는 구조라, 호출한 쪽을 따로 인증하지 않는다. Hermes에는 우리 게이트웨이처럼 주인 확인과 카톡 비공개 규칙이 아직 다 옮겨지지 않았다.
고른 것
허용 목록에 있는 도구만 부를 수 있게 했고, 지금은 memory_search, route_search, map_search, android_screen 네 개만 열었다. 승인이 필요한 도구는 기본 거부다. 모르는 인자는 거절하고, 예외 메시지에서 민감한 내용을 숨긴다. 기존 게이트웨이가 떠 있으면 MCP 서버가 시작을 거부해 Android를 두 프로세스가 동시에 만지지 않게 했다.
버린 것
Hermes 기본 도구 묶음을 다 켜는 방식은 범위와 요금이 통제되지 않아 뺐다.
대가
지금 Hermes 경로로는 카톡 전송, 메일, 예약 추가가 안 된다. Discord DM 승인 흐름을 Hermes 작업자에 연결해야 열 수 있다.

정해진 흐름은 n8n, Agent는 이름만 안다 동작 중

캘린더, 알림, 상태 점검 같은 반복 흐름을 어디에 둘까

상황
매번 같은 순서로 도는 일까지 모델이 단계마다 판단하면 토큰이 샌다. Google 캘린더 같은 연동은 n8n에 이미 노드가 있다.
고른 것
n8n을 서버 내부 포트에만 띄우고, Agent에는 n8n_list와 n8n_run 두 도구만 준다. 부를 수 있는 워크플로는 주인이 파일에 적어 둔 이름뿐이고, 요청에서 URL을 받지 않는다. 실행은 승인이 필요하고 실패해도 자동으로 다시 부르지 않는다.
버린 것
모델이 n8n 주소를 직접 고르게 하는 방식은 프롬프트 주입 한 번으로 아무 주소나 부를 수 있어서 뺐다.
대가
워크플로를 하나 추가할 때마다 사람이 이름을 등록해야 한다. 지금 등록된 것은 health_check 하나다.

공개 채널과 개인 정보를 섞지 않는다 동작 중

서버 채널에서 멘션으로 부를 때 무엇까지 보여 줄까

상황
DM만 받다가 공개 채널 멘션에도 그 채널에 답하게 바꿨다. 기억에는 개인 사실이, 카톡 결과에는 남의 대화가 들어 있다.
고른 것
채널별 대화 기록을 DM 기록과 분리했고, 저장된 개인 사실은 공개 채널 프롬프트에 자동으로 넣지 않는다. 승인 버튼은 항상 주인 DM으로 간다. 카톡에는 답장 문장만 보내고, Discord에는 카톡 내용이나 스크린샷 대신 완료·실패 상태와 사용량만 남긴다.
대가
공개 채널에서는 대비스가 나에 대해 아는 것을 일부러 덜 쓴다.

실험은 모델을 부르지 않고 잰다 완료

토큰 절감 효과를 어떻게 숫자로 보여 줄까

상황
처음에는 전략별로 실제 모델을 수백 번 호출해 비교하려 했다.
고른 것
구독 모델을 실험용으로 대량 자동 호출하는 방식은 일반 사용 범위를 벗어날 수 있어서 중단했다. 토크나이저로 입력 크기를 계산하는 오프라인 측정으로 바꾸고, 결과 품질은 운영 답장에 찍히는 토큰 기록으로 확인하기로 했다.
대가
여러 번 호출할 때 쌓이는 비용과 답의 품질은 이 측정에 없다.

6. 다음에 붙일 것과 안 붙일 것

최근 Agent 도구는 많지만, 이 서버(4GB, 추가 요금 0원)에서 "이걸로 실제로 하는 일"이 분명한 것만 골랐다.

도구판단맡길 역할과 이유
MCP이미 씀우리 도구를 Hermes, 기존 게이트웨이, 앞으로 붙일 다른 클라이언트가 같이 쓰게 하는 경계다.
LangGraph붙인다본체를 바꾸는 용도가 아니다. 멈췄다 이어 가는 일에만 쓴다. 예를 들어 배달 주문을 결제 직전에 멈추고 Discord 승인을 기다렸다가, 서버가 재시작돼도 그 지점부터 이어서 결제한다.
Obsidian붙인다기억을 마크다운 노트로 두고 Git이나 Syncthing으로 PC·휴대폰과 맞춘다. Agent가 무엇을 기억하는지 사람이 직접 읽고 고칠 수 있다.
RAG붙인다Obsidian 노트를 sqlite-vec와 작은 다국어 임베딩으로 색인한다. 관련 노트 몇 개만 모델에 보내므로 기억이 늘어도 입력이 같이 늘지 않는다.
음성붙인다Discord 음성 메시지를 faster-whisper로 받아쓰고, 답은 Piper나 Kokoro로 읽어 준다. 둘 다 서버 CPU에서 돌아 토큰이 들지 않는다.
Google 캘린더붙인다n8n 워크플로로 만든다. 날짜와 시간은 코드가 해석하고, 애매한 표현만 모델에 넘긴다.
PC·휴대폰 노드서버만 있음기기가 서버로 먼저 연결하므로 집 공유기 포트를 열지 않는다. 메시지는 최대 한 번만 전달하고, 전달 여부가 불확실하면 다시 보내지 않는다.
Langfuse안 붙인다DB를 따로 띄워야 해서 4GB 서버에 무겁다. 답장마다 찍는 토큰 기록과 로그로 대신한다.
Ollama안 붙인다CPU만으로는 느리고 메모리를 많이 먹는다.
browser-use류안 붙인다화면을 보며 단계마다 모델을 불러 토큰이 많이 든다. 정해진 사이트는 Playwright 스크립트가 낫다.
Mem0류미룬다Hermes에 기억 계층이 이미 있다. Obsidian을 붙인 뒤에 다시 본다.

7. 아직 모르는 것

4GB 서버에 Android, n8n, Hermes를 같이 올렸을 때 여유는 설치 직후 측정값(약 2.2GB)뿐이다. 동시에 일을 시켰을 때 버티는지는 재지 않았다. 카톡 로그인은 앱 재시작까지 유지되는 것을 봤지만, Android 재부팅이나 장기 세션 만료 뒤에도 남는지는 모른다. 카톡 사진 전송은 시험하지 않았다. Hermes와 기존 게이트웨이를 같은 작업으로 비교한 실험도 아직 없어서 "Hermes가 더 낫다"는 근거는 기능 범위뿐이다. 토큰 절감 80%는 직접 만든 요청 세트로 계산한 값이라, 실제 대화 기록으로 다시 재야 한다.
